24 октября 2026. База: `4d70a6cea87d794016b572f250b65d70c84e4bd4`.

## Что подтверждает журнал

Исследован пользовательский экспорт `capsule-logs-2026-10-24_15-08-31.txt`
из release-сборки `4d70a6c`. Файл с пользовательскими данными в git не добавлялся.
В экспорте 21 начало DOWNLOAD-разрешения через `WEB_REMIX` и семь отмеченных
bot-check в DOWNLOAD. Очередь переходила к следующей композиции и снова
обращалась к WEB_REMIX. Перенос пользовательского порядка воспроизведения в
загрузчик оказался регрессией: массовая загрузка использовала основной аудиоклиент.

В журнале токен уже присутствует, первые запросы успешно возвращают поток.
Первый холодный resolve в экспорт не попал: начальная композиция использует URL
возрастом около 21 секунды. По этому файлу нельзя измерить ожидание генерации
токена или доказать единственную причину серверного challenge. В частности,
`poToken=false` в player-запросе WEB_REMIX само по себе не ошибка: закреплённый
manifest требует токен для GVS, а не для player request. Его правила не менялись.

## Холодное воспроизведение

- При непрогретом обязательном токене временно первым выбирается `VISIONOS_0_1`,
  если он присутствует в настроенном наборе. В InnerTubeX 0.5.2 это automatic-профиль;
  `VISIONOS` 1.02 имеет статус probe-only и описан как способный задерживаться в
  чистых Android-сессиях. Он остаётся резервом. Явный исходный приоритет Vision
  или Embedded не меняется этой политикой.
- Порядок вычисляется после получения места в scheduler, по текущей готовности
  токена. Настройки не перезаписываются; при готовом токене используется исходный
  порядок для следующих разрешений. Уже играющий поток не заменяется.
- Фоновый startup warmup готовит только общий visitor-bound minter. Убраны
  получение resolver mutex, предварительный extractor/config/cipher проход и
  mint токена для тестового PREWARM_VIDEO_ID. Эти дополнительные операции не
  нужны для запуска первого Vision-потока. Конечные бюджеты PoTokenSession сохранены.

## Отдельная политика скачивания

`DownloadUtil` вызывает `CapsuleAudioEngine.resolveDownload`. Его порядок:

`VISIONOS_0_1 → WEB_EMBEDDED_PLAYER → VISIONOS`

Он не зависит от аудионастроек, состояния прогрева или повышения приоритета
воспроизведения той же композиции. Для него используется отдельный экземпляр
extractor с отдельным config cache и без TokenProvider. Он не запускает WebView,
не mint-ит токены и не потребляет foreground WEB-сессию. Поддержка остальных
клиентов воспроизведения сохраняется.

У скачивания отдельный per-media карантин. Его 403/410 не исключают профиль из
воспроизведения, а успешный download не заменяет запомненный аудиоклиент. Ручной
повтор/удаление загрузки очищает только её карантин. Сохранены проверка полного
кеша, совместимость частичных байтов, два CDN rollover, три попытки профиля,
сохранённый DownloadIndex и существующее распределение запросов 3.2–5.8 секунды.

Bot-check прекращает текущую цепочку загрузки без смены identity и открывает
отдельный 60-секундный gate для очереди. Он проверяется до входа в scheduler и
перед сетевым разрешением. Повторные заблокированные обращения не продлевают
deadline. Gate использует монотонное время, не создаёт таймеров/polling и не
блокирует воспроизведение. HTTP 429 по-прежнему открывает общий защитный breaker.

Общие транспорт, cipher service и scheduler сохранены: не создаётся второй
параллельный сетевой конвейер для массовых /player-запросов. Разделение локальных
политик не гарантирует независимости серверных ограничений одного IP/аккаунта.

## Проверки и практические ограничения

Добавлен интеграционный тест на настоящей закреплённой InnerTubeX с MockEngine:
PoTokenSession удерживается внутри незавершённого создания minter, а Vision 0.1
в это время возвращает поток одним player-запросом, без запроса PoToken. После
освобождения minter проверяется возврат WEB-приоритета. Это проверка зависимости
и порядка запросов, не измерение времени первого звука на телефоне.

Новые тесты также проверяют token-free download-план и резервы, независимость
двух карантинов одной композиции, конечный cooldown без скользящего deadline и
отсутствие глобальной блокировки воспроизведения после download challenge.
Первый локальный прогон: 561 core-тест приложения без ошибок (ранее 557);
JSON runtime и debug APK успешны. Проверки CI включают повторный core-набор,
innertube, Android lint и подписанный universal release APK.

Физическое устройство к окружению не подключено. Новая версия требует повторного
полевого прогона холодного старта и очереди скачивания на сети пользователя.
Token-free download-профили могут не поддерживать private/uploads, age-restricted
или отдельные explicit-композиции; их отказ не превращается в автоматическую
массовую нагрузку на WEB_REMIX/WEB_CREATOR. Не обещается скачивание любого контента.
Если ограниченное ожидание DownloadUtil/повторы Media3 исчерпаны во время cooldown,
композиция остаётся в DownloadIndex как failed и может потребовать ручного повтора
после cooldown. Неполный файл не объявляется успешно скачанным.
